ProbMoE: Differentiable Probabilistic Routing for Mixture-of-Experts

Heng Zhao1 Zilei Shao2 Guy Van den Broeck2 Zhe Zeng1

1 University of Virginia  ·  2 University of California, Los Angeles

PDF Citation Code

Abstract

Mixture-of-Experts (MoE) models scale by activating only a small subset of experts per token. However, training such models remains challenging because top-k routing is discrete and non-differentiable, requiring gradient estimators for expert selection whose design remains a central open problem. We introduce ProbMoE, a probabilistic routing framework that models expert selection as a distribution over cardinality-constrained expert subsets and formulates routing as probabilistic inference in this discrete subset space. We first propose ProbMoE Exact-k routing, which samples k-expert subsets in the forward pass, and the backward pass uses gradients through each expert's exact marginal probability as a tractable surrogate for the true gradient. ProbMoE naturally generalizes to a dynamic-k routing setting, where both training and inference constrain the routing cardinality to the same predefined range, allowing adaptive expert allocation per token. Across benchmarks and model backbones, ProbMoE Exact-k achieves strong performance compared to competitive baselines, with improved expert utilization and routing diversity; ProbMoE Dynamic-k achieves comparable performance with fewer activated experts.

01 · Exact-k

A distribution over valid subsets

Instead of committing to a deterministic ranking during training, the router samples from all expert subsets with exactly k members.

02 · Gradient

Exact marginals as the surrogate

The forward mask stays hard and sparse; the backward pass follows each expert's exact inclusion probability under the constrained distribution.

03 · Dynamic-k

Cardinality becomes inferable

Conditioning on a range rather than one fixed k lets the router choose both expert identity and the amount of computation per token.

00

The block

ProbMoEOlmoeSparseMoeBlock subclasses OLMoE’s own OlmoeSparseMoeBlock and is swapped in at load time, so the rest of the model is untouched:

# finetune/finetune.py
from models.v2.probmoe_v2 import ProbMoEOlmoeSparseMoeBlock
olmoe_module.OlmoeSparseMoeBlock = ProbMoEOlmoeSparseMoeBlock

It adds no parameters — same 193 tensors, same state_dict keys as a stock OLMoE block. A pretrained checkpoint loads and saves unchanged. All it changes is how the router logits are interpreted.

The problem it solves

The router emits one logit per expert and must pick exactly k. Two requirements conflict:

  • the forward pass needs a genuine discrete choice — a hard 0/1 mask with exactly k ones, because only k experts actually run;
  • the backward pass needs a gradient, and a sampled discrete mask has none.

ProbMoE treats expert routing as probabilistic inference over cardinality-constrained expert subsets and leverages SIMPLE (Ahmed et al., 2023) as its gradient estimator. Each router logit θi defines a Bernoulli parameter pi = σ(θi); conditioning on exactly k active experts induces the routing distribution. ProbMoE samples a valid k-expert subset from this distribution in the forward pass and uses the exact marginal μi = P(zi=1 | Σz = k) as the backward surrogate. One compiled circuit supplies both quantities.

The rest of this page opens up the training branch, using a block with 4 experts and top-2, where

p      = [0.8,      0.6,      0.4,      0.2]      # sigmoid(router_logits)
logits = [1.38629,  0.40547, -0.40547, -1.38629]

Only C(4,2) = 6 expert subsets are possible, so each circuit operation remains small enough to inspect directly.

01

The circuit

The constraint “exactly 2 of 4 are true” is compiled once, offline, into a DAG — a smooth, decomposable, deterministic circuit. It is built by splitting the variables into pairs and merging: first decide how many of {x1, x2} are on, then how many of {x3, x4}, and combine the ways that sum to 2.

For n=4, k=2 that gives 15 nodes: 8 literals, 6 group nodes, 1 root. Every node has a fixed integer id; the arrays never change during training.

Two structural facts to carry forward. Determinism: the root’s three elements cannot both fire for the same assignment, so summing their weights counts each subset exactly once. Sharing: x1 is a single node reachable from two parents, [12 ch 1] and [12 ch 2] — the reason stage 4 sums two terms.

02

Upward pass

Seed each literal with its weight, then work bottom-up. For each node: multiply the two children of each element, sum over the elements. In code (levelwiseSL, all in log space, one batched op per level):

for level in levels:
    theta[level] = data[idx2primesub[level]].sum(-2)   # log w(prime) + log w(sub)
    data[level]  = theta[level].logsumexp(-2)          # the node's inside value
    theta[level] -= data[level].unsqueeze(1)           # normalize → log P(element | node)

The line that does the real work

theta[level] -= data[level] divides every element weight by its node’s total (a subtraction, since this is log space), converting raw weights into a probability distribution over that node’s elements — conditional on a descent having reached the node.

This single normalization is what makes the same tensor serve both jobs that follow: it is the categorical distribution the sampler draws from in stage 3, and the multiplier the flows use in stage 4 — which is why the marginals come out already normalized, with no division by Z at the end.

Reading the root’s three numbers

At the root the normalization answers a concrete question: how do the two picks split between the two variable groups? Each element covers a disjoint set of the six subsets, so its probability is exactly their combined mass.

In words: a 53.5% chance both chosen experts come from the first pair, 45.0% one from each, and just 1.5% both from the second — which is what you’d expect when p₁ and p₂ are the large probabilities. Note e0 and e2 each have only one completion below them, so their probability is a single subset’s probability; e1 fans out into four, and resolving that fan is what the next level down does.

03

Sampling

Sampling walks down from the root. At each active node, draw one element from its normalized distribution, then activate that element’s two children. Where the descent lands on a positive literal, that variable is 1.

Because the root’s elements are mutually exclusive and each level’s choices are independent given the parent, every root-to-leaf path corresponds to exactly one subset, and its path probability is that subset’s conditional probability. Enumerating all of them reproduces the target distribution exactly:

How the code tracks this

Rather than recursing per node, sample_subset processes a whole level at once and propagates activation with a counter, so shared children are handled correctly:

active_count[root] = 1
for level in reversed(levels):            # levels is bottom-up, so this is top-down
    probs = theta[level].softmax(dim=-2)  # already-normalized log-probs → probabilities
    choice = torch.multinomial(probs, 1)  # one element per node, batched
    for child in selected_children:       # prime and sub
        active_count.index_put_(child, parent_active, accumulate=True)

return (active_count[pos_literals] > 0)   # the k-hot mask

Nodes whose parent never activated still draw a choice — it is simply discarded, which keeps the whole level a single batched operation. Padded elements point at a sentinel row and are masked to zero probability.

04

Marginals

The marginals need no differentiation and no second pass over the inputs. Set the root’s flow to 1 and push downward: a node’s flow is the probability that a descent visits it.

data[root] -= data[root]                  # flow(root) = log 1 = 0
for level in reversed(levels):
    data[level] = (theta[parent, elem] + data[parent]).logsumexp(-2)

Level 0 simply inherits the root’s element probabilities. The interesting step is the literals, where sharing means two routes arrive at the same node:

Order matters

The downward pass overwrites data in place: inside values are replaced by flows as it descends. So the call order in probmoe_routing is not cosmetic — sample_subset(theta) must run before marginals_from_upward(data, theta). Swap them and the sampler reads a corrupted workspace.

05

Backward

Now the payoff. The forward value must be the hard sample z; the gradient must come from the smooth marginals μ. The straight-through estimator gets both from one line:

g_full = (samples - marginals).detach() + marginals
w_full = g_full * softmax(router_logits)

In value, g_full == z exactly — the detached bracket cancels μ. In gradient, ∂g/∂θ = ∂μ/∂θ, because the detached part contributes nothing. So the forward pass is genuinely discrete while the backward pass sees a differentiable surrogate.

The identity that makes it work

Differentiating the marginals through the circuit gives, exactly, the covariance of the conditioned distribution:

∂μ / ∂θ  =  Cov(z_i, z_j | Σz = k)

06

v1 vs v2

Both implementations produce the same two routing objects: a hard exact-k sample for the forward pass and an exact marginal vector for the backward surrogate. The difference is how they get there.

v1 Dynamic program
  1. Build the DP tableRun over experts and subset cardinalities.
  2. Sample by a backward walkMake sequential Bernoulli choices through the table.
  3. Run the DP again with a graphDifferentiate logZ to obtain exact marginals.
  4. Backpropagate through that derivativeThe loss triggers a grad-of-grad through the DP.
Cost shapetwo DP passes + second-order backward
v2 Compiled circuit
  1. Compile the constraint onceReuse the exactly-k circuit at every training step.
  2. Run one upward passCache inside values and local conditional probabilities.
  3. Read both outputs from the cacheSample by batched descent; compute marginals by downward flow.
  4. Use ordinary backpropagationThe loss differentiates one first-order computation graph.
Cost shapeone upward pass + first-order backward
Shared forward outputexact-k binary sample z
Shared backward surrogateexact marginals vector

Measured on GSM finetuning, both jobs running concurrently on identical hardware, steady-state seconds per optimizer step:

v1  107.0 s/it     266 tokens/s
v2   76.4 s/it     403 tokens/s      # about 29% faster

Read per-step deltas, not tqdm's s/it average - early iterations are dominated by model load and compile warmup.

Running it and the code map

Reproduce every number on this page:

cd /p/simple/sparse_attention/own_simple_v2

Turn v2 on for a training run — the flag flows into both the output directory name and the log name:

V2=True bash train/olmoe/script/train_ProbMoE_OLMoE_exact.sh

And the whole routing pipeline, as it appears in probmoe_routing:

self.simple = Simple_Layer(self.num_experts, self.top_k)   # once, at __init__

log_p       = log_sigmoid(router_logits.float())
data, theta = self.simple.upward(log_p)                    # stage 02
samples     = self.simple.sample_subset(theta)             # stage 03  (no_grad)
marginals   = self.simple.marginals_from_upward(data, theta).exp().permute(1, 0)   # stage 04

g_full = (samples - marginals).detach() + marginals        # stage 05
w_full = g_full * F.softmax(router_logits, dim=1)
_, selected_experts = torch.topk(samples, self.top_k, dim=-1)
router_weights = torch.gather(w_full, 1, selected_experts)
